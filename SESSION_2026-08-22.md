# What was accomplished — 2026-08-21/22

A performance arc, end to end: from a solver that ran the minimal channel in
~35 days to one that runs it in ~14, plus the measurement infrastructure that
established which of several plausible directions were real — and, as often,
which were not.

Detail lives in `3D_STATUS.md` §7M–§7O, `GPU_PORT_PLAN.md` and
`TORCH_VERIFY_PLAN.md`. This is the account of the whole thing.

---

| | |
|---|---|

| **GPU, fused CUDA vs 20-core numba, full step** | **1.25×** |
| **Minimal channel** | ~35 days (Mac) → **~14 days** (Spark, fused CUDA) |

## 3. The performance chain, all measured

### CPU

| change | gain | acts on |
|---|---|---|
| row-7 down-weighting | **5.39×** | iterations |
| numba fusion (~30 passes → 1) | **4.01×** | cost per iteration |
| `workers=1` at small `Nz` | **1.32×** | thread-pool overhead |
| **composed** | **21.7× / 28.5×** | measured, not multiplied |

### GPU

| | |
|---|---|
| operator alone (`apply_L` + `apply_Lᵀ`) | 3.3–3.9× vs Mac numba |
| **whole preconditioned solve** | **4.23×** vs Spark numba, **3.7×** vs Mac numba |
| host↔device penalty if the loop leaves the GPU | **21.9×** — erases everything |

Phase 2 beat its own forecast: the plan predicted 2–2.5× end-to-end because `gs`,
the vector operations and the reductions would become a larger share once the
operator sped up. Moving them onto the device instead made the *whole solve*
better than the operator alone.

## 4. Decisions, each settled by measurement

| question | answer | basis |
|---|---|---|
| Fuse or compile? | **Fuse** | bandwidth-bound; compiling BLAS calls buys nothing |
| MLX on the M3 Max? | **Impossible** | Metal has no FP64; FP32 unusable at κ ≈ 1e4 |
| DGX Spark? | **Yes** | 141.8 GB/s FP64 vs the Mac's best 33.6 |
| PyTorch or cuPyNumeric? | **PyTorch** | 5.4× at 88³; the drop-in form is Legate's *slowest* |
| Port for the minimal channel? | **Yes** (reversed) | the 4.5-day estimate measured at ~35 days |
| Fuse `_dot`? | **No** | hypothesis tested and refuted |
| Block-Jacobi / p-multigrid / fast-diag | **No** | measured, rejected |

## 5. Two retractions

**12.74× → 21.7×.** The first net-net took one leg of an A/B from a stored JSON
written by an earlier, thermally-loaded process. Measured back-to-back in one
process, numba was worth 4.0× on that case rather than 2.36×.
→ **L14: stored results are a record, not a control.**

**"MLX wins, the Spark loses" → exactly backwards.** `mx.array()` silently
downcasts float64 → float32 (and complex128 → complex64), so the probe measured
FP32 and labelled it FP64. Metal has no double precision at all, so the
recommendation pointed at a platform that *cannot run this solver*. Caught by the
user, not by the suite.
→ **L15: a benchmark that does not assert its own dtype is not a measurement.**

## 6. Bugs found — all silent, none raised an exception where it mattered

| bug | how it would have hurt |
|---|---|
| `np.asarray(kz)` on a tensor | **406 host transfers per 200 CG iterations** — correct answers, GPU advantage spent on PCIe |
| kernel facade forcing `device()` | CPU tensors in, CUDA out; silent per-call transfer in a device-resident loop |
| `id(mesh)`-keyed cache | id reuse after GC → a new mesh gets a dead one's index map; surfaced as **one flaky failure** that three clean runs would have dismissed |
| circular import in both kernel modules | numba survived on import ordering alone; torch did not |
| `spectrum.py` hardcoded a Mac path | it is *imported by the suite*, so the whole suite was unportable |
| `.gitignore` nested-`npz` rule | trailing comments are not syntax — the rule had **never** worked; 45 checkpoints uncovered |
| `pmg_sweep_N8_nz16.json` | held pre-row-7 numbers contradicting its own write-up |

Two test-design errors of my own, both caught by the tests failing on correct
code: a `±2` iteration gate calibrated for 1100-iteration solves applied to a
3950-iteration one, and an `err < 1e-6` solution gate that ignored κ·tol.

## 7. The minimal channel

Rig built at the standard wall normalisation (`δ=1, u_τ=1, ν=1/180, f_x=1`).
Three things were wrong in the inherited Stage 5 rig and all three were fixed:
it ran at **Re_τ ≈ 16** (its `re=180` is a *bulk* number), in a **full-sized box**
(Lx⁺ = 2262 against Jiménez–Moin's ~350), with a **streamwise-independent trip**
that by Squire's theorem cannot sustain turbulence.

Gates pass: Lx⁺ = 565, Lz⁺ = 192 (above the JM minimum, deliberately not on it);
Δx⁺ = 11.8, Δz⁺ = 6.0 (finer than KMM); y₁⁺ = 1.00; laminar control gives
`u_τ` = 0.993 against the prescribed 1.0 and `U_bulk` = 15.45 against KMM's ~15.6.

**And the price gate broke §8.6's estimate**: 4786 CG/stage, 114–150 s/step,
CFL = 3.44 at `dt = 2e-3` — **~35 days, not 4.5**. That measurement is what
reversed the porting decision.

## 7b. The GPU port, and where its win actually came from

| step, minimal channel | wall | vs incumbent |
|---|---|---|
| numba, 20 CPU cores (Spark) | 75.7 s | 1.00× |
| torch GPU, unfused | 129.3 s | 0.59× |
| **fused CUDA** | **60.4 s** | **1.25×** |

**Most of the available win came from moving off the Mac, not from the GPU.**
~35 days → ~17.5 days is the machine; ~17.5 → ~14 is the GPU.

Four hypotheses were refuted by measurement along the way, and each would have
sent work the wrong way:

* *"the complex explicit path will be the GPU's weakness"* — it is its greatest
  strength (convection **18.2×**, `apply_L0_complex` **23.2×**);
* *Phase 4's alarming 0.6×* — an artifact of one GPU stream against 20 CPU
  threads. Against **serial** numba, torch is 4.2×, matching the solve benchmark;
* *"fusing `_dot` will recover the missing factor"* — refuted at 4.28× serial vs
  3.64× threaded;
* *"warm start is worth 1.5–3×"* — **0.9%**.

The fused kernel confirmed its own diagnosis exactly: the GPU was 9–23× on every
large single operation and only 3.17× on the 30-launch matvec, i.e. **launch-
bound**; fusing it gave 5.24×. But the step improved only 1.25×, because `gs` and
the CG vector operations are now ~75% of a step — §7M's "34% outside the kernel",
returning *because* the kernel got faster.

## 7c. The iteration count: two attacks, both small

4794 CG/stage is the untouched multiplier. Two hours-scale attempts:

| | result |
|---|---|
| warm start (`x0`, never previously passed) | **0.9%** — structural: `x=0` is already close for a *defect* correction |
| `ROW7_WEIGHT` re-tune at production mesh | **~6%** — the curve plateaus by 1e−5; keep 1e−4 |

**The sweep corrected a documented figure by 2.7×**, though: the row-7
down-weighting is worth **14.6× at production scale**, not the 5.4× recorded from
a 3×3-element rig. It remains the largest single change this solver has had, by a
wider margin than was known.

What remains — deflating the near-null `(ω_x, ω_y)` cluster §7J identified, or a
real multilevel preconditioner — is days of work, not hours.

## 7d. The runs, and what they cost to learn (2026-08-23)

Two minimal-channel runs launched, both retired — see §7P.

**`minchan_001`, 14 h:** healthy on every logged diagnostic, and carrying
**relative divergence of 1.1e−01** against the validated Stokes case's 5e−09.
Cause: a non-solenoidal random trip. LSSEM penalises `div u` as a weighted row
and does not project the state, so divergence in the *initial condition* is never
removed. Fixed by building the noise as the curl of a vector potential:
3.2e−01 → 1.0e−04.

**`minchan_002`, 16 h, retired at t = 1.170:** every budget closed, divergence
pinned at its floor to three figures, CFL steady — and **relaminarised**, because
making the noise solenoidal also made it 1.8× weaker (`rms_w` 0.243 → 0.135) and
dropped it below the bypass-transition threshold. `rms_w` fell 20% monotonically
with no inflection. A correct fix for one problem created another: it was checked
against the divergence it was designed to fix, not against the amplitude it
incidentally changed.

The compensation is that **the solver was faultless for 1170 steps**, which
demonstrates the instrumentation added after `minchan_001` can tell a sound run
from a contaminated one — at a cost of 16 h rather than 12 days.

**Five hypotheses refuted en route**, the last of which was mine and embarrassing:
I derived a momentum balance assuming `∫(u·∇u) = 0`, which holds only for an
exactly divergence-free field — the very thing §L5 of this project says is never
true in a least-squares formulation.

**→ L16: a run can look healthy on every diagnostic you are logging.** The
defence is a conservation law logged from step one and a validated reference to
compare against; both are cheap, and worthless if built only after something
looks wrong.

## 8. Where it stands

**Done:** M6; GPU triage; PyTorch backend Phases 1–2, verified on the GB10.

**Also done since:** Phase 3 (FFT/convection on device), Phase 4 (device-resident
driver), and a **fused CUDA kernel** (`kernels_cuda.py`) — parity 3.478e-16,
**5.24× the matvec**. Backend is now `numpy` / `numba` / `torch` / `cuda`.

**Next:** Phase 5 (physics validation: Stokes decay to 8 significant figures, M2,
Stage 5) → checkpointing → the run.

**Open, and honestly so:**

* a full time *step* is not yet measured on GPU — only the solve;
* gather-scatter's CUDA atomics make results non-deterministic unless
  `deterministic(True)` is set — a production decision not yet taken;
* whether the minimal channel **stays turbulent** is unknown, and the minimal
  unit is intermittent by design;
* full M7's cost estimate inherits the same iteration bracket the minimal
  channel just broke, so it should be re-priced from a measured step;
* ~290 hardcoded Mac paths remain across ~135 scratch scripts.
